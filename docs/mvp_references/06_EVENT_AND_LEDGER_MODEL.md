# Event and ledger model

The ledger is the authoritative record of all threat entries and their state transitions.  It must be append‑only, auditable and immutable—once a record is written, it is never modified.  The ledger stores structured events representing lifecycle changes, evidence associations and feedback.  This document specifies the event types, their fields and how they are persisted.

## Tables and persistence

The ledger uses a relational database (SQLite) with the following core tables:

| Table | Purpose | Key fields |
|------|--------|-----------|
| `entries` | Stores the static attributes of a `ThreatEntry`, including `id`, `observables`, `state`, `attack_techniques`, `tlp_label`, `created_at`, `updated_at`. | `id` (primary key). |
| `entry_events` | Records every lifecycle transition as a `LifecycleEvent`. | `event_id` (primary key), `entry_id` (foreign key), `timestamp`, `from_state`, `to_state`, `actor`, `notes`. |
| `entry_evidence` | Many‑to‑many table linking entries to evidence digests. | `entry_id`, `digest`. |
| `entry_feedback` | Stores feedback digests associated with an entry. | `feedback_id` (primary key), `entry_id`, `digest`, `timestamp`. |
| `proposals` | Stores validator proposals. | `proposal_id`, `entry_id`, `validator_id`, `action`, `confidence`, `timestamp`, `signature`. |
| `decisions` | Stores consensus decisions. | `decision_id`, `entry_id`, `action`, `timestamp`, `notes`. |
| `decision_proposals` | Many‑to‑many linking decisions to supporting proposals. | `decision_id`, `proposal_id`. |

Each table has an auto‑incrementing surrogate key (where appropriate) and timestamps.  SQLAlchemy ORM models reflect these tables and provide relationships for easy traversal.

## Event types

### Entry creation (`CREATE_ENTRY`)

* Occurs when a new threat entry is created via `POST /ledger/entries`.
* Writes to `entries` with state set to `suspected` and timestamps.  For each provided evidence object, a record is inserted into `entry_evidence` linking the entry and digest.
* An initial event may be recorded in `entry_events` with `from_state = null`, `to_state = suspected` and `actor = "creator"`.

### State transition (`STATE_TRANSITION`)

* Occurs when the consensus controller, coverage oracle or timeout workflow posts to `/ledger/entries/{id}/transitions`.
* Valid transitions are: `suspected→confirmed`, `suspected→review`, `suspected→deprecated`, `confirmed→review`, `review→confirmed` and `review→deprecated`.
* A `LifecycleEvent` record is appended with the `from_state`, `to_state`, `actor` (e.g., `consensus`, `oracle`, `timeout`) and optional notes.  The entry’s `state` and `updated_at` fields are updated accordingly.
* The ledger enforces that transitions follow the allowed state graph and rejects invalid transitions.

### Feedback recorded (`FEEDBACK`)

* Occurs when an endpoint agent posts a feedback digest via `/ledger/entries/{id}/feedback`.
* Inserts a record into `entry_feedback` linking the entry and feedback digest with a timestamp.
* Feedback does not change the lifecycle state but is important evidence for validators during revalidation.

### Timeout / expiry (`TIMEOUT`)

* A background task in the ledger periodically scans entries for stale states:
  * `suspected` entries older than a configured threshold (24 h) with no recent proposal activity in the active timeout window are automatically moved to `review`.
  * `review` entries older than a configured threshold with no recent proposal activity in the active timeout window are moved to `deprecated`.
* Direct `suspected→deprecated` remains available as an explicit transition path, but it is not the default timeout automation in the shipped POC.
* These transitions produce a `STATE_TRANSITION` event with `actor = "timeout"` and no supporting proposals.

## Event sequencing

Events are always inserted in chronological order.  When reading an entry, the ledger reconstructs the lifecycle by ordering `entry_events` by `timestamp`.  The `history` field in the API response contains a list of these events.

## Auditability and immutability

* **Immutability:** Records in `entry_events`, `proposals`, `decisions` and `feedback` are never updated or deleted.  If a correction is required, a new record is appended explaining the correction.
* **Provenance:** Each event records the actor responsible.  Consensus decisions record the proposal IDs that contributed to the outcome.  Signatures in proposals provide cryptographic proof of authorship.
* **Timestamp source:** Lifecycle, decision and feedback timestamps are generated by the server. Proposal and coverage report timestamps are provided by the submitting component and recorded after validation.

By formalising event types and persistence rules, the ledger service can guarantee an auditable history of every state change and provide validators and auditors with reliable ground truth.


## Central check events (optional demo, 2026-10-12)

`central_check_events` records unique event IDs, entry references, active flags,
reasons, evidence digests, timestamps and an ordering sequence. The latest event
controls only the supplemental-check flag for a confirmed entry. It does not change
threat lifecycle state; absent events default to active. See
[CENTRAL_DEMO](../CENTRAL_DEMO.md) for simulation and trust boundaries.
